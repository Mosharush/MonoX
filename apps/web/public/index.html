Delivery contract

A visible path from scaffold to deployment artifact

Every stage has an input, an owner, and a gate. Autoscaling stops at the ceiling you configure.

  1. 01

    Generate

    Start with synthetic apps, workspace metadata, and optional infrastructure adapters.

  2. 02

    Work in bounds

    Apps consume packages. Infrastructure stays independent from product source.

  3. 03

    Verify

    Identify affected workspaces for targeted validation. Public CI still runs repository rules, tests, builds, and deployment validation across the full repository.

  4. 04

    Render with limits

    Generate workload manifests with probes, budgets, policies, and a bounded autoscaling maximum.

The architecture stays legible from code to runtime

MonoX keeps reusable behavior, product code, and deployment adapters in separate zones. Each layer depends in one direction and exposes a versioned contract to the next.

  1. Apps Runnable API and web workspaces
  2. Reusable packages Workspace rules and versioned contracts
  3. Schemas and renderers Validated deployment inputs
  4. Delivery artifacts Docker Compose and Kubernetes

Applications may depend on packages. Packages never depend on applications. Infrastructure renders product-independent artifacts without importing application source.

What MonoX is not

MonoX is not a replacement for your package manager, container runtime, or Kubernetes control plane.

It generates, validates, and explains delivery artifacts. Applying those artifacts remains an explicit, protected operation. Production secrets stay in external secret stores, and every scaling policy keeps a configured maximum.
